# Portfolio App — Agent Context

## What this is
A multi-tenant SaaS where users sign in with Google and get an editable personal portfolio at `/<username>`. The portfolio is always public (no draft/private mode). The owner edits directly in the live design — no separate admin panel or forms. The root domain (`/`) shows a product landing page.

## Stack
- **Next.js 16 App Router** (Turbopack, `src/` not used — everything is under `app/`)
- **Supabase**: Auth (Google OAuth via PKCE), Postgres, Storage (bucket `portfolio-media`), Row Level Security
- **Tailwind CSS** (`dark-*` palette, `dark-50` = lightest, `dark-900` = darkest)
- **TypeScript** throughout

## URL structure
- `/` — Product landing page (`app/page.tsx`). Signed-in users get redirected to their portfolio.
- `/login` — Google sign-in (`app/login/page.tsx`)
- `/[username]` — Portfolio page (`app/[username]/page.tsx`). Owner sees edit affordances; add `?preview=1` to see visitor view.
- `/admin` — redirect to owner's portfolio
- `/auth/callback` — Supabase PKCE callback

## Key env vars
- `ROOT_USERNAME` — the portfolio username that maps to the root domain (set in Vercel, baked at build time for client components). Owner of that portfolio gets their page at both `/` and `/<username>`.
- `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` — Supabase connection (public; fine to expose).

## In-place editing pattern
The core UX: the owner sees dashed outlines on every text field while in editing mode. Clicking focuses a `contentEditable` span. Changes are held in **draft state** (React context) until the owner clicks **Save** in the floating edit bar.

### LanguageContext (`app/context/LanguageContext.tsx`)
The single source of truth for all client-side state. Key fields:
- `editing: boolean` — true when the owner is in edit mode
- `dirty: boolean` — true when there are unsaved changes
- `draft` — the in-progress content object
- `setField(path, value)` — updates a single field in the draft (dot-notation path, e.g. `"projects.items.2.narrative.0"`)
- `updateActive(path, value)` — updates the active language only
- `updateBoth(path, value)` — updates both EN and ES
- `markSaved(savedDraft)` — clears `dirty`, but only if `savedDraft` (the exact draft object the caller actually sent to `savePortfolio`) is still the current draft. See "Save race: an edit made while a save is in flight" below for why this isn't unconditional.
- `lang` — which language the portfolio's own **content** is shown/edited in (the EN/ES pill toggle in `Navbar`, `toggleLang`). Also drives `t` — see "App language vs. content language" below for why that's the correct scope for it, after getting it wrong once.
- `uiLang` / `setUiLang(lang)` — which language the **owner's own private tools** are shown in (`uiT`: the onboarding tour, and the app-language dropdown's own label). Deliberately narrow — see below.
- `blocks` / `updateBlock(blockKey, lang, block)` — migrated rich text fields; `updateBlock` patches one field's local copy right after its own autosave succeeds, since nothing on that path calls `router.refresh()`. See "Rich text fields (Tiptap)" below for why this exists.

Content paths are resolved by `app/lib/content-path.ts`.

### App language vs. content language
`lang` and `uiLang` used to be the same single state variable (`t: translations[lang]`, `content: draft[lang]`) — one toggle switched both the portfolio's content *and* every button/label around it at once. Raised as a real product gap, not a bug report: someone building a portfolio worldwide might want its content in English for an international audience without that also forcing their own editing tools into English, or vice versa — "su idioma base no es necesariamente español."

**First attempt (wrong): made `t` itself follow the new `uiLang` instead of `lang`.** That silently broke the content-language toggle for almost everything *except* the raw text fields — `t.nav.*` (every nav link, plus the CV modal), `t.contact.*`, `t.footer.*`, `t.projects.gallery.*` (aria-labels and the gallery badge), `t.skills.certifications` all stayed frozen at whatever `uiLang` happened to be, ignoring the content toggle entirely. Reported live: "muchas partes de mi portfolio no pasan a ingles a español y viceversa." The mistake was scope: all of those are part of the **portfolio's own bilingual presentation** — a visitor reading the Spanish version of someone's page should see "Historia/Proyectos/Habilidades/Contacto" in the nav, not whatever language *that visitor's own browser* happens to prefer. Only a handful of things are genuinely the *owner's own private tooling*, independent of which content language is on screen: the onboarding tour (never shown to a visitor at all), and the app-language dropdown's own label (self-referential — it's the control for `uiLang`, so its own text should follow `uiLang`).

**The fix**: `t` reverted to `translations[lang]` (content-following, exactly like it worked before `uiLang` existed at all) — so `Navbar`'s nav links and CV modal, `Contact.tsx`, `Footer.tsx`, `ProjectTimeline.tsx`'s gallery labels, and `Skills.tsx`'s "Certifications" heading are back to tracking the content-language toggle correctly. A **second**, narrower object — **`uiT`: `translations[uiLang]`** — covers only `OnboardingTour.tsx` and `AppLanguagePicker.tsx`'s own label, the two places that actually are the owner's private preference rather than page content. `EditBar`'s "Saved!"/"¡Guardado!" flash was never part of `t`/`uiT` to begin with (a hardcoded ternary) and correctly checks `uiLang` directly — it's genuinely owner-only tool feedback, not portfolio content.

- **`lang`** (content language) works exactly as it always did — the EN/ES pill toggle in `Navbar`, `toggleLang()`, driving both `content`/`draft[lang]` *and* `t`. Every existing call site that reads `lang` from context (`Skills.tsx`'s `deleteSkillCategoryData(cat.id, lang)`, `updateActive`/`updateBoth` internally) still means exactly what it meant before either `uiLang` PR.
- **`uiLang`** is the owner's private preference, used only via `uiT` in the tour and the app-language dropdown itself — nowhere else. Before reaching for `uiT` in a new spot, ask: would a visitor with no relationship to this owner ever see this text as part of the page? If yes, it wants `t` (content language), not `uiT`.
- **Detected once from the browser, not tied to any account**: `detectBrowserLang()` reads `navigator.language`; the very first hydration on mount picks a stored `localStorage` value if one exists, otherwise this browser detection. Per-device, not a profile setting — no migration, no server round trip.
- **Only an explicit pick persists** — the auto-detected value updates React state but is deliberately *not* written to `localStorage` until the owner actually opens the dropdown and picks a language themselves (`setUiLang`, which does both). Auto-detection is idempotent, so there's nothing to "remember" about it on its own.
- **`app/components/AppLanguagePicker.tsx`** — the dropdown itself, hanging off what used to be a plain `<Link href="/">{initials}</Link>` logo in `Navbar` (now a button; the implicit "click the logo to go home" behavior was traded away for this). Same open/close-on-outside-click/Escape shape as `BackgroundPicker.tsx`. Shows `FlagUS`/`FlagES` + "English"/"Español", highlighting whichever `uiLang` is currently active.
- **The one-time browser-locale hydration is a `useState` boolean guard, not a `useRef`** — reading/writing a ref's `.current` during render (outside the one sanctioned `if (ref.current == null)` lazy-init shape) is exactly what this project's `react-hooks/refs` lint config flags; a second `useState` toggled inside the same render-time conditional (the same pattern already used for `mounted` below and EditBar's `justSaved` flash) sidesteps it without needing an effect at all.
- Verified live (Playwright): with `t` correctly back on `lang`, clicking the content toggle now flips `Navbar`'s nav links *and* `Skills.tsx`'s "Certifications" heading together (`"Story"/"Certifications"` → `"Historia"/"Certificaciones"`); picking a *different* app language from the dropdown afterward leaves both exactly where the content toggle put them, confirming `uiT`'s scope stayed correctly narrow this time.

**The content-language toggle's own selected-state indicator was separately reported as "no se ve claramente cual esta seleccionado, quedo fijo en ingles"** ("can't tell which one's selected, seems stuck on English") — not actually a functional bug (traced and confirmed `toggleLang`/`lang` were flipping correctly the whole time), but the mobile version genuinely had nothing to fix: it only ever rendered the language you'd switch *to* (`lang === 'en' ? <ES/> : <EN/>`), never showing which one was currently active at all. Desktop's own indicator (bold text-color-only on a `text-xs` pill) was real too, just less severe — legible in isolation, easy to miss in the corner of a navbar at a glance. Both are now the same solid-pill treatment used elsewhere in this file for a selected option (`BackgroundPicker`, `AppLanguagePicker`'s own dropdown): the active language gets `bg-dark-50 text-dark-900 font-bold`, the inactive one stays a muted `text-dark-400` — and mobile now always renders *both* EN and ES (like desktop already did), so there's something to visibly move between. Verified with a screenshot before/after a click at both viewport widths.

### EditableText (`app/components/EditableText.tsx`)
A `contentEditable` span. Empty fields must have `data-placeholder` and the CSS class `editable-field` so they get a visible placeholder (see `app/globals.css`). Without this, empty `contentEditable` collapses to zero height and becomes unclickable.

### EditBar (`app/components/EditBar.tsx`)
Floating bottom bar. Shown only to the owner. Has: Preview link (`?preview=1`), Save button (calls `savePortfolio`). Registers a `beforeunload` guard when `dirty === true` to warn on navigation. Only reflects fields still on the plain draft/Save system below — a migrated rich text field autosaves on its own and never touches `dirty`. Now that nearly every field has migrated to autosave, `dirty` only ever flips for the handful of things still on the draft system — add/remove/reorder, and the few plain-text fields (contact email/socials) — so **typing into a rich text field will never enable the Save button**; that's correct, not a bug. There used to be an idle-state hint span here explaining this ("Text saves automatically — Save is for reordering/adding") — removed after a report that the save/no-save split still wasn't clear from text alone. The per-field save-status pill in `FloatingToolbar.tsx` (see the Tiptap section above) now carries that job instead, showing live "Saving…"/"Saved" right at the field being edited rather than as a static disclaimer at the bottom of the screen.

Since that hint alone wasn't reassuring enough on its own, the button itself now flashes a confirmation too: `LanguageContext`'s `lastBlockSavedAt`/`notifyBlockSaved()` is a signal separate from `dirty`, bumped by `useBlockPersistence` every time *any* field's autosave actually completes (not scheduled — completes). `notifyBlockSaved` is wrapped in `useCallback` in the provider (not an inline arrow in the context value) specifically so it's a stable reference — this context re-renders on every keystroke into an old-system field, and an unstable function in `useBlockPersistence`'s own `useCallback` deps would tear down and re-attach every mounted editor's `update`/`blur` listeners on each one. `EditBar` turns `lastBlockSavedAt` into a ~1.6s "Saved!"/"¡Guardado!" flash (scale + a lime glow, `AnimatePresence`/`framer-motion` for the label swap) — turning the flash *on* happens via the render-time state-comparison pattern (comparing the incoming value against one held in state, not a bare `useEffect` calling `setState` synchronously, which the `react-hooks/set-state-in-effect` rule flags), while a separate effect keyed on the same value only ever schedules/clears the timer that turns it back *off* (a `setTimeout` callback triggering `setState` asynchronously is fine — the rule specifically targets a synchronous call in the effect body itself). Keying that effect on `lastBlockSavedAt` (not on the `justSaved` boolean it sets) is what makes a second save arriving while still flashing restart the timer instead of the flash silently expiring early.

The button also carries a live **"Saving…"** state now, sourced from `LanguageContext`'s `blockSaving` (`true` while at least one field's autosave request is in flight — a ref-counted `savingCount`, not a plain boolean, since more than one field can be mid-save at once). This replaced an earlier attempt at a *separate* per-field indicator in `FloatingToolbar` — rejected on report ("tiene que ser dual, todo en el mismo boton": one button, not two indicators in two places) in favor of folding it into this same button, which is also where the "Saved!" flash above already lives. `useBlockPersistence.save()` calls `notifyBlockSavingStart()` right before `upsertBlock` and `notifyBlockSavingEnd()` in a `finally` — the `finally` (not just the success/error/conflict branches) is what fixes a real "stuck on Saving…" bug reported separately: `upsertBlock` itself *rejecting* (a network failure, a revalidate mid-flight, anything that throws rather than resolving to `{ok:false}`) used to leave that field's local `status` sitting at `'saving'` forever, since nothing after the `await` ever ran to change it. A `catch` block was added alongside the `finally` for the same reason, so the field's own error toast still shows too. `notifyBlockSavingEnd` floors the counter at 0 (`Math.max(0, n - 1)`) so a double-decrement (e.g. the unmount-flush effect saving a field that just finished saving through the normal path) can't drive it negative and get `blockSaving` stuck `true`.

**Save race: an edit made while a save is in flight used to get silently discarded.** `onSave` snapshots `draft` at click time and awaits `savePortfolio`. Nothing disables `updateActive`/`updateBoth` while that request is in flight — only the Save button itself (`disabled={state==='saving'||!dirty}`). Found by a QA pass, not a live report: batch a couple of edits, click Save, then (before the slow request resolves) add a project or edit the contact email — that second edit only ever touched local `draft` state and was never part of the request already sent. The old `markSaved()` cleared `dirty` unconditionally on a successful response, so the button flipped to "Saved" and disabled itself, and the `beforeunload` guard (gated on `dirty`) stopped warning — closing the tab now silently lost the second edit, with the UI actively telling the owner it was safe to leave. Fixed by having `markSaved` take the exact draft object that was actually sent (`markSaved(savedDraft)`) and only clear `dirty` if that's still the current draft — compared against a `draftRef` kept in sync via a `useEffect` (so the comparison reads the *latest* draft, not a stale closure from whenever the async save callback was created). If an edit landed in between, `dirty` stays `true` and the button stays live so a follow-up click actually sends the newer content. Verified directly against the real `LanguageContext` logic (no Supabase needed — this is a pure client-state race) with a scratch harness simulating a slow save: an edit made mid-flight correctly leaves `dirty=true` after the save resolves, while the no-intervening-edit case still correctly clears it.

### Orphaned data on delete (projects, chapters, skill categories)
Removing a project/chapter/skill category (the old array-based system — see "Drag-to-reorder" below) only ever filters the entity out of the relevant array in `content`, persisted by the next Save. That system has never touched `portfolio_blocks` or `portfolio_media` — so before this fix, every one of a removed entity's migrated fields (title, narrative, tags, metrics, chapter body, category name + its nested skills) and, for projects/chapters, its photos (`portfolio_media` rows *and* the underlying Storage files) were orphaned forever, keyed by an id nothing could ever reference again. Found by a QA pass, not a live report — invisible to the owner (the row just disappears from the page), but an unbounded, silent leak in both the database and the storage bucket.

Fixed with three new server actions in `portfolio-actions.ts`, each called immediately from the component's remove handler (fire-and-forget, `void`'d — same "immediate action, not deferred to Save" pattern the block-list system already uses for its own add/remove) right alongside the existing `updateBoth`/`updateActive` array mutation:
- **`deleteProjectData(projectId)`** (`ProjectTimeline.tsx`'s `removeProject`) — deletes every `portfolio_blocks` row matching `projects.items.<id>.%` in **both** languages (removal always uses `updateBoth`, so the id is meant to be shared cross-language), plus every `portfolio_media` row for that project and its Storage files.
- **`deleteChapterData(chapterId)`** (`Journey.tsx`'s `removeChapter`) — same shape for `journey.chapters.<id>.%`, both languages, plus the chapter's one photo (mirrors `removeChapterPhoto`'s own media/storage cleanup, but this is the removal path that never called it).
- **`deleteSkillCategoryData(categoryId, lang)`** (`Skills.tsx`'s category `onRemove`) — deletes `skills.categories.<id>.%` blocks for **only the active language**, not both: unlike projects/chapters, a category is removed via `updateActive` (categories aren't kept in sync across languages the way project/chapter ids are), so deleting both languages' blocks here could wipe the *other* language's still-referenced category if its own array hasn't had the same removal applied yet.

### Drag-to-reorder (projects, journey chapters)
Both `p.items`/`chapters` are still plain arrays in `portfolios.content` (only their individual fields moved to blocks — see below), so reordering them is just a local draft mutation via `updateBoth`, exactly like add/remove — no server action, no `sort_order` column, nothing persisted until the owner hits Save.

- **`app/lib/reorder.ts`** — `moveBeforeId(items, movedId, targetId)` moves the entity with `movedId` to sit right before the one with `targetId`, by id rather than index. Applied identically to *both* languages' own arrays inside `updateBoth`, since the two arrays aren't guaranteed to be in the same index order (only the same set of ids) — replaying the move by id against each language's own array independently keeps both in sync regardless.
- **`app/components/EditControls.tsx`**'s `DragHandle` — a small grip icon, and deliberately the *only* draggable element in the row (`draggable` lives on the handle, not the whole card/chapter). A row full of `contentEditable`/Tiptap fields would otherwise fight the native HTML5 drag gesture with the browser's own text-selection-drag the moment a user's mousedown happened to land on or near editable text. The row itself only needs `onDragOver`/`onDrop` (no `draggable`) to accept a drop — this is the same split already used by `EditableProjectGallery`'s photo tiles, just scoped to a dedicated handle instead of making an entire (text-free) tile draggable.
- Both `ProjectTimeline.tsx` and `Journey.tsx` track `dragId`/`overId` locally (component state, not context) — the dragged card gets `opacity-40`, a valid drop target gets an `outline` ring. `onDrop` calls `moveBeforeId` via `updateBoth` and clears both ids; a drop on the dragged item itself is a no-op.
- Testing native HTML5 DnD with Playwright: `page.dragAndDrop()`/mouse-simulated drags do **not** reliably fire real `dragstart`/`dragover`/`drop` events. Dispatching `new DragEvent(type, { bubbles: true, dataTransfer: new DataTransfer() })` directly on the source/target elements works, but each dispatch must be its own `page.evaluate()` call with a real wait after it (e.g. `waitForTimeout(150)`) — batching all four events (dragstart/dragover/drop/dragend) into one synchronous `evaluate()` fires them all before React ever re-renders, so `dragover`'s and `drop`'s handler closures still see the pre-drag `dragId` (null) and silently no-op. A real user's drag has natural time between these; a synthetic test needs to fake that gap explicitly.

## Rich text fields (Tiptap) — migration in progress
A field-by-field replacement of the plain-text system above with rich text (bold/italic/underline/strike, font size, color, highlight, link, alignment), landing in `portfolio_blocks` instead of `portfolios.content`. Migrated so far: the original 15 top-level scalar fields (a title, a tagline, a name — see 0005), project narrative lines (see 0006, the first list-shaped field), a scalar field but keyed by a *dynamic* parent id rather than a fixed path — chapter tag/heading/body (`journey.chapters.<chapterId>.tag`/`.heading`/`.body`) and project title (`projects.items.<projectId>.title`), see 0007 — two more plain string lists, project tags (`projects.items.<projectId>.tags.<tagId>`) and `contact.availableItems.<itemId>` (the latter not nested under any per-entity array at all — there's only one contact section per portfolio), see 0008 — and, see 0009: project metrics, which turned out NOT to be an owner-addable/removable list at all (the layout is a fixed 3-column grid, always exactly 3) — each is a fixed-index scalar block, `projects.items.<projectId>.metrics.<i>.label`/`.value` with `<i>` literally `0`/`1`/`2`, same family as the chapter/title fields, not sorted by `sort_order` — and certifications, the first *multi-field* list (`skills.certs.<certId>.title`/`.issuer`, see "Multi-field list-shaped fields" below). Also see 0010: skills categories — an addable/removable list of entities that each *also* own a nested addable/removable list (their skills), the last and trickiest of these migrations, since `SkillCategory` never had a stable id the way `Project`/`JourneyChapter` always have. 0010 assigns one (deterministic, `skillCategoryId(index)` = `"skillcat-<index>"`, matching `projectId()`/`chapterId()`'s own scheme) by rewriting `portfolios.content` directly — every migration before it only ever inserted into `portfolio_blocks`, never touched the JSONB column. The category entity's own structural existence (its id) still lives in `portfolios.content`, exactly like a chapter's or project's id — only its *fields* (`category` name, and its nested `skills` list) move to blocks. `normalizeContent` (portfolio-db.ts) and the save-path sanitizer (`portfolio-actions.ts`'s `list(skills.categories, ...)`) both independently backfill/preserve that id the same deterministic way, so a category never loses or lacks one. And, see 0011, the last two scalar-field stragglers: project `year`/`tag` (dynamic parent id, same family as project title) and hero `stats.<i>.value`/`.label` — like project metrics, NOT an owner-addable/removable list (fixed 3-column grid, always exactly 3), so fixed-index scalar blocks rather than list machinery; `stats` sits directly under `content` rather than nested per-project, so there's no parent id to interpolate into its block_key. This closes out the migration entirely except contact socials/email, kept on the old plain-text system for good: `contact.socials.url` was deliberately *not* migrated despite being a plain string field — `Contact.tsx` uses it as a real `<a href>`, not just to display text, the same reasoning that already excluded `contact.email`; `contact.socials.label` was left alongside it on the old system too, rather than half-migrating one field of a two-field item while the other stays behind.

A migrated field nested inside a clickable card (project title, inside the photo card that opens the photo manager on click) needs its own `onClick={(e) => { if (editing) e.stopPropagation() }}` on its wrapper — otherwise a click meant to focus the text bubbles up to the card's own handler and steals it into opening the photo modal instead (fixed in ProjectTimeline.tsx's "Year + title overlay" div). Only guarded behind `editing`, so a visitor's click still opens the lightbox/gallery exactly as before.

The same card also needs the matching `onKeyDown={(e) => { if (editing) e.stopPropagation() }}` on that same wrapper, not just `onClick` — the outer card's own `role="button"` accessibility handler treats a keyboard Enter/Space as "activate" (opens the photo modal) and calls `preventDefault()` on Space specifically to stop the page from scrolling, which — same bubbling problem as the click — also silently eats every space bar keystroke typed into the title/year fields (reported: "si aprieto la barra espaciadora me abre para subir fotos y no puedo poner espacios"), not just Enter.

### List-shaped fields (narrative lines, and the pattern for the rest still to come)
Unlike a scalar field's single fixed `block_key`, a list's items share one **key prefix** — a narrative line is `"projects.items.<projectId>.narrative.<lineId>"`, where `<lineId>` is a fresh random id meaning nothing beyond uniqueness. Render order comes from the `sort_order` column (already on the table since 0001, unused by the scalar fields since they have no siblings), never from parsing the key or object insertion order.

- **`app/lib/editor/useBlockList.ts`** — reads `blocks` from context, filters to keys starting with `${prefix}.`, sorts by `sortOrder`. Exposes `add()`/`remove(blockKey)`, both immediate actions (not autosave) with a `busy` flag, matching the existing photo add/remove pattern rather than useBlockPersistence's debounce. Also exposes `reorder(movedBlockKey, targetBlockKey)`, added after a report that narrative lines/tags/contact items had no way to reorder at all (only projects/chapters did, via the plain-array `moveBeforeId` — see "Drag-to-reorder" above). Unlike that plain-array reorder, a block list autosaves immediately, so this can't just stage a local mutation: it reuses `moveBeforeId` (treating each item's `blockKey` as its `id`) purely to compute the new order client-side, then calls `reorderListItemBlocks` to persist every item's new `sort_order` in one round trip, then `router.refresh()`. Wired into `ProjectNarrative.tsx`, `ProjectTags.tsx`, and `Contact.tsx`'s availableItems the same way `ProjectTimeline.tsx`/`Journey.tsx` wire the plain-array version — local `dragKey`/`overKey` state, a `DragHandle`, `opacity-40`/outline-ring feedback.
- **`app/lib/block-list-actions.ts`** — `addListItemBlock(prefix, section, lang)` inserts one new empty block at `max(sort_order) + 1` among that prefix+lang's existing rows. `removeListItemBlock(blockKey, lang)` just deletes the row — sibling sort_orders are left with gaps, which is fine since order only depends on relative value, not contiguity. `reorderListItemBlocks(orderedBlockKeys, lang)` resequences every block in the list to its index in the given array (one `update` per block, run concurrently) rather than computing a single fractional `sort_order` for just the moved item — simpler, and cheap enough for lists this size.
- Lists are **not** kept in sync across EN/ES — same as the plain-text system's `updateActive` (vs `updateBoth`, used only where structural identity like a project/chapter id must match across languages). A project can end up with a different number of narrative blocks per language.
- A list needing its own hook call (`useBlockList`) can't be inlined inside a parent's `.map()` over a dynamic-length array (projects, in this case) — that violates the Rules of Hooks, since the number of hook calls would vary between renders. `ProjectNarrative.tsx`, `ProjectTags.tsx`, and `SkillCategoryCard.tsx` (one per skills category, itself rendered from `Skills.tsx`'s categories `.map()`) exist as their own components for exactly this reason. `contact.availableItems` and `skills.certs`, by contrast, aren't nested under any per-project/per-category loop, so `Contact.tsx`/`Skills.tsx` call the hook directly with no wrapper needed.

### Multi-field list-shaped fields (certifications, and the pattern for skills categories still to come)
A list whose items carry more than one field each (a certification's title + issuer; a metric's label + value, if metrics were ever made addable) needs one more level of indirection than `useBlockList`'s single `block_key` per item: every field of one item shares a **key prefix plus item id**, `"<listPrefix>.<itemId>.<field>"` (e.g. `"skills.certs.<certId>.title"` / `"skills.certs.<certId>.issuer"`), and one `sort_order` between them, so the item — not the individual field block — is the add/remove unit.

- **`app/lib/editor/usePairedBlockList.ts`** — the multi-field counterpart to `useBlockList`. Groups `blocks` by item id (parsed off the tail of each matching key against the known `fields` list, not by insertion order), sorts groups by `sortOrder`, and returns `items: { itemId, blockKeys: Record<field, blockKey> }[]` — a caller renders one `RichText` per `blockKeys.<field>`.
- **`app/lib/block-list-actions.ts`** — `addPairedListItemBlock(prefix, fields, section, lang)` generates one fresh item id and inserts one row per field, all sharing that id and one `sort_order` (`max + 1`, read the same way as the single-field version). `removePairedListItemBlock(prefix, itemId, lang)` deletes by `like '<prefix>.<itemId>.%'` — every field of that item in one statement, rather than one delete per field.
- A backfill migration generating item ids per pre-existing item (0009's certs) must generate the id **before** cross-joining against the field list — doing it after would fan each item out into N rows (one per field) and give each field row of the *same* item a different random id, breaking the pairing. Generate it once in an inner subquery, then cross-join fields against that already-materialized result.
- Not every multi-field item's fields are equally safe to migrate: `contact.socials`' `url` is read as a real `<a href>`, not just displayed, so — like `contact.email` — it stays on the old plain-text system, and `label` was left there alongside it rather than split across two systems.

- **Tiptap v3**, not v2 — v2's entire version range has an unpatched XSS/prototype-pollution disclosure (GHSA-cp6q-959q-f8rh) in `mergeAttributes()`; the fix only landed in 3.30.4+.
- **`app/lib/editor/render-html.ts`** — turns a block's Tiptap JSON into HTML **without** Tiptap's own `generateHTML` (that needs a DOM/jsdom to run server-side, which this app doesn't otherwise depend on). Hand-rolled instead: `renderBlockHtml` walks the JSON directly and is whitelist-only by construction — it can only ever emit the tags in its `MARK_TAGS` map plus `<p>`, regardless of what the JSON claims, so there's no injection surface to sanitize against. `sanitizeDoc` strips a client-submitted doc to the same whitelist before it's ever stored (a server action can be called directly, bypassing the editor UI). `renderInlineHtml` renders without the outer `<p>` — used wherever a field is embedded inside a page element that already carries its own typography (a heading, an existing `<p>`), where a nested `<p>` would be invalid HTML.
- **`app/lib/block-actions.ts`** — `upsertBlock(blockKey, lang, section, json, expectedUpdatedAt)`. Conflict check: if the stored row's `updated_at` has moved past `expectedUpdatedAt`, the write is refused and the caller's `latest` value comes back instead of silently overwriting it.
- **`app/lib/editor/useBlockPersistence.ts`** — autosaves one Tiptap editor 800ms after the last keystroke, or immediately on blur/unmount so a quick navigation right after typing doesn't lose the debounce window. `save()` JSON-round-trips `editor.getJSON()`'s output (`JSON.parse(JSON.stringify(json))`) before it's ever passed to the `upsertBlock` server action — **required**, not defensive cleanup: ProseMirror builds each node's `attrs` via `Object.create(null)` internally, so `getJSON()` hands back objects with no `Object.prototype`. React's server-action argument serialization doesn't treat that as plain data — it substitutes an opaque "temporary client reference," which server-side code then can't read properties off of. Surfaced live as a genuinely broken save on *any* field with text alignment applied — `render-html.ts`'s `paragraphAlignStyle`/`sanitizeDoc` reading `node.attrs?.textAlign` on the server is what actually throws, with the exact error text `"Cannot access textAlign on the server. You cannot dot into a temporary client reference from a server component."` Reproduced and confirmed fixed directly in the sandbox (this one doesn't need live Supabase — it's a pure client/server-boundary serialization bug, throws before any DB call happens) by autosaving a center-aligned field and checking the resulting error is the ordinary "You are not signed in." rather than the temporary-reference crash.
- **`app/components/editor/EditableText.tsx`** — the migrated counterpart to the plain one, addressed by the same dot-path `block_key` (e.g. `"hero.name"`) content-path.ts already resolves. Not editing → renders `renderInlineHtml` via `dangerouslySetInnerHTML`. Editing → dynamically imports `RichEditableField.tsx` (`next/dynamic`, `ssr: false`) — **this is the boundary that keeps Tiptap out of a public visitor's bundle entirely.**
- **`app/components/editor/FloatingToolbar.tsx`** — `@floating-ui/react`, anchored to a *virtual* reference computed from `editor.view.coordsAtPos` (caret or selection bounding rect), not a real DOM node. Framer Motion `AnimatePresence`, spring on enter / 120ms ease-out on exit, opacity-only under `prefers-reduced-motion`. `useFloating({ transform: false })` — floating-ui defaults to positioning via `transform: translate(...)`, which Framer Motion's own `transform`-driven scale/y animation was silently overwriting (toolbar rendered pinned at its unpositioned top-left corner); `top`/`left` positioning avoids the collision. Subscribes to the editor's `transaction` event to force a re-render on every selection/formatting change — `editor.isActive()`/`getAttributes()` read live editor state at render time, which React has no way to know changed on its own when the toolbar was already open.
- **Save status lives in exactly one place: EditBar's Save button.** A per-field pill in `FloatingToolbar` was tried first (shown right at the caret while typing) but was explicitly rejected — two separate save indicators on screen at once (the toolbar pill *and* EditBar's flash) was the opposite of "dual", not the "one button, dual-purpose" the report actually asked for. `FloatingToolbar` no longer takes a `status` prop or renders anything related to saving. See "EditBar" above for how the button itself now shows live autosave status via `LanguageContext`'s `blockSaving`.
- **Font size** — `@tiptap/extension-text-style` ships an official `FontSize` extension (`editor.commands.setFontSize('16px')`, a raw CSS string, not the number spec'd originally). `app/lib/editor/extensions/fontSize.ts` holds the shared `FONT_SIZES` whitelist both the toolbar's stepper+dropdown (`toolbar/FontSizeControl.tsx`) and the server-side sanitizer check against. Mirrors Tailwind's own text-size scale (12–96px) rather than an arbitrary list — these fields sit inline among Tailwind-styled headings (the hero name renders at 60px via `text-6xl`), so the options cover what's already on the page. The toolbar's readout shows the *actual* computed size at the selection (`getComputedStyle`), not just an explicit mark — otherwise text with no mark at all (inheriting its size from a surrounding heading class) would show nothing despite being visibly huge. Real inline `font-size` on a real `<span>`, so surrounding layout reflows exactly like any other browser text resize, no special handling needed.
- **Font family** — `@tiptap/extension-text-style`'s official `FontFamily` extension (`editor.commands.setFontFamily(...)`, stored on the same `textStyle` mark as font size/color). `app/lib/editor/extensions/fontFamily.ts` holds the `FONT_FAMILIES` whitelist (10 curated stacks — "Sans"/"Mono" deliberately reproduce the page's own existing `font-sans`/`font-mono` defaults, per the user's explicit ask to keep those selectable alongside the new options) that both `toolbar/FontFamilyControl.tsx` and the server-side sanitizer check against. All ten are OS-provided fonts, not `next/font`/Google Fonts loads — no extra network request, no flash of unstyled text, and the public read view renders identically to the editor without needing to load anything. **Values are single-quoted, not double** (`"Georgia, 'Times New Roman', serif"`) — they're spliced into an HTML `style="..."` attribute in `render-html.ts`, which is itself double-quoted, so a literal `"` in the value would close that attribute early. `FontFamilyControl` mirrors `ColorSwatches`' "computed value" fallback (reads `getComputedStyle(...).fontFamily` when no explicit mark is set) and its "Default"/unset option.
- **Alignment has no visible effect on some fields** — a Tiptap paragraph's `text-align` needs a box *wider than its own text* to have anything to redistribute into; several fields' wrapping elements don't provide one. Concretely: a `<span>`/`<h3>`/`<h4>` sitting as a **direct flex-row item** (e.g. `<div className="flex items-start justify-between">` wrapping a field next to a `RemoveButton`) has no `flex-grow`, so it shrink-wraps to its own content width — text-align then has zero slack to move text within, silently doing nothing regardless of which alignment the toolbar shows as active. Confirmed on `ProjectTimeline.tsx`'s project tag and `SkillCategoryCard.tsx`'s category name (both fixed with `flex-1 min-w-0` on the field's own wrapper) and `Journey.tsx`'s chapter tag+heading wrapper (fixed by giving the *shared* wrapping `<div>` around both fields `flex-1 min-w-0`, since neither tag nor heading is itself the flex item there). By contrast, a field that's a flex-**column** item with no `align-items` override (default `stretch`) already gets real width for free — this is why `ProjectTimeline.tsx`'s year/title fields (inside `flex flex-col justify-end`) never needed this fix. Verified by measuring an actual text node's rendered position (`Range.getBoundingClientRect()`) before/after toggling center alignment — comparing element *widths* alone is unreliable, since a shrink-wrapped `<p>` always exactly matches its own child's width whether or not the wrapper itself received real slack from its parent.
- **Strikethrough/color/highlight/link/alignment** — `@tiptap/extension-highlight`, `@tiptap/extension-link`, `@tiptap/extension-text-align`, plus `Color` (also bundled in `@tiptap/extension-text-style`, same package as `TextStyle`/`FontSize` — no separate `@tiptap/extension-color` install needed). `app/lib/editor/extensions/colors.ts` holds the `TEXT_COLORS` swatch whitelist (a curated palette, not a free-form picker) and the shared `HIGHLIGHT_STYLE` (single fixed color, used by both the Tiptap extension config and the serializer so edit and public-read views match). Link `href` goes through a strict `isSafeHref` whitelist (`http(s)://...` or a well-formed `mailto:` only) in **both** the editor's own normalizer (`LinkPopover.tsx`, prepends `https://` to a bare domain) and `render-html.ts`'s `sanitizeDoc`/`sanitizeMark` — verified directly: a raw `{href: 'javascript:alert(1)'}` payload calling `sanitizeDoc` straight (bypassing the editor UI) comes back with the mark dropped entirely. `LinkPopover`'s text input needs real DOM focus to type into (unlike every other control, which uses `onMouseDown+preventDefault` to never take focus from the editor) — `FloatingToolbar` tracks a `linkOpen` ref and skips its hide-on-blur while the popover is open, or the toolbar would vanish the moment the input gets focus. Opens via `Cmd/Ctrl+K` (window-level keydown, `preventDefault` to stop the browser's own address-bar shortcut).
- **StarterKit v3 already bundles `Link` and `Underline`** — registering either one again alongside it makes Tiptap log `Duplicate extension names found: ['link','underline']` and warn that it can misbehave. Both are configured *through* `StarterKit.configure({ underline: {}, link: {...} })` instead of added as separate extensions; it's the same registration either way. This warning was firing on every field before it was noticed on the landing demo's console, where it's public rather than only in the owner's editor.
- **`useEditor` runs with `immediatelyRender: true`.** The usual reason to set it false is Tiptap's SSR warning, which cannot apply here: `RichEditableField` is only ever reached through `next/dynamic(..., { ssr: false })`, so it never runs on the server at all.
- Each editable field disables **Enter** (`editorProps.handleKeyDown`) — these are short, single-paragraph fields (a name, a title), not multi-paragraph documents, and the inline renderer above assumes exactly one paragraph.
- Placeholder CSS: a Tiptap field is never truly `:empty` like the plain contentEditable span (it always contains a paragraph element), so it needs its own rule — `.ProseMirror p.is-editor-empty:first-child::before` in `globals.css`, alongside the existing `.editable-field:empty:before` rule the plain fields still use.
- **A migrated (scalar, Tiptap-backed) field kept showing/editing whichever language's content it happened to load at mount, no matter how many times the content-language toggle was clicked afterward.** `useEditor`'s `content` option only seeds the Tiptap document once, at creation — it's not reactively synced on later renders (standard, documented Tiptap/ProseMirror behavior; there's no built-in "update the document when this prop changes" wiring). `EditableText.tsx` renders `<RichEditableField initial={block} .../>` with no `key`, so toggling `lang` re-renders the *same* component/editor instance with a new `initial` prop that the already-created Tiptap instance never looks at again. Autosave itself was never broken — `RichEditableField` reads `lang` fresh via `useLang()` every render and passes it straight through to `useBlockPersistence`, which correctly writes to the right language's block row — only the *display* was stuck, silently editing (and re-saving over) the wrong language's content. Reported live, verbatim: "hice el portfolio en español y ahora tampoco cambia a ingles… Edite la parte de mi historia" — every scalar migrated field across the whole portfolio (hero, journey chapters, project title/year/tag, footer, contact subtitle, skills subtitle, ...) had this, which is why it looked like "muchas partes" rather than one field. Fixed with `key={`${blockKey}:${lang}`}` on `<RichEditableField>` — forces a full remount (and therefore a fresh Tiptap instance seeded from the correct language's `initial`) on every language switch, rather than trying to imperatively resync a persistent editor instance via `editor.commands.setContent()` in an effect (more moving parts, and this exact class of field already has a dedicated fallback for a remount's brief gap — see `.rich-field-fallback` below, which is recomputed from `blocks[blockKey][lang]` on every render independent of any editor instance, so there's nothing new to keep in sync). Reproduced and confirmed both ways in the sandbox (doesn't need live Supabase — a pure client-side remount bug): typing into a field with `lang='es'`, toggling to `'en'`, and reading the field's own text back — without the `key`, the Spanish text was still sitting there; with it, the field correctly reset to the (empty) English content.
- **The `key`-per-language fix above immediately surfaced a second, related bug: a field's own just-saved content vanished back to stale/empty the moment the owner toggled away from its language and back.** `blocks` (in `LanguageContext`) used to be a static passthrough of whatever `portfolio.blocks` the server sent on the very first page load — nothing on the scalar-field autosave path ever called `router.refresh()`/updated it afterward, deliberately, so typing doesn't risk a disruptive remount elsewhere on the page mid-edit (unlike the block-*list* system's add/remove/reorder, which already does call `router.refresh()` on success — see "List-shaped fields" below). Before the `key` fix, that staleness was invisible: the same in-memory Tiptap instance just kept showing whatever the owner had actually typed, regardless of what stale data `blocks` held underneath. After it, every language switch forces a fresh remount that reads straight from `blocks` — so a field the owner had already typed into *this session*, immediately after toggling away and back, silently reverted to whatever it looked like before they'd started editing. Confirmed directly: type into a field, toggle to the other language and back, read the field's text — it reverted. Investigated after a report of unpredictable-seeming cross-language content changes ("cambio un texto y se cambia en el otro tambien igual"); a direct field-to-field leak between languages was specifically tested for and not found (typing distinguishable text into one language and immediately checking the other showed the other language's own, unrelated, correctly-empty content) — the revert-on-toggle-back above is the concrete, reproducible bug, and the most likely source of what read as "changes in the other one too."

  Fixed with a new `updateBlock(blockKey, lang, block)` on `LanguageContext`, backed by real state (`blocksState`, seeded from `portfolio.blocks` and only otherwise resynced when that prop's own `.blocks` reference changes — i.e. after a genuine `router.refresh()` from elsewhere, using the same render-time-comparison pattern as `uiLangHydrated` above, not an effect). `useBlockPersistence.save()` calls it right after a successful `upsertBlock` (and on a conflict, with the server's `latest` version) — `upsertBlock`'s success response was extended to echo back the *sanitized* `json`/`html` it actually stored, so the locally-cached copy matches the server exactly rather than trusting whatever the client optimistically sent. This keeps a field's own edits visible across a language round-trip without ever calling `router.refresh()` — the exact disruption during typing this was designed to avoid in the first place. Verified live: injecting a fake successful save via `updateBlock` directly (the sandbox can't drive a real save without Supabase) and then toggling away and back shows the injected content, not the stale pre-session value.
- **A migrated field's wrapper must be `<div>`, never `<p>`** — in edit mode, `RichEditableField`'s `EditorContent` renders its own `<div>` (Tiptap/ProseMirror's contentEditable root), and a `<div>` inside a `<p>` is invalid HTML: the browser's parser auto-closes the `<p>` early and React flags the resulting DOM restructuring as a nesting error. This had been sitting latent in several places since each field's original migration (`hero.greeting`/`.tagline`/`.description`, both hero `stats.<i>` fields, `projects.subtitle`/`.ctaDescription`, `footer.tagline`/`.rights`, `journey.chapters.<id>.body`, `contact.subtitle`, `skills.subtitle`, a cert's `.issuer`) — the public, non-editing render path uses a `<span>` via `renderInlineHtml` instead, which is why it never showed up outside edit mode. Found while debugging a narrative-line report by rendering `ProjectNarrative` directly (its own `<p>` wrapper had the same bug) in a scratch harness with `editing: true` — something none of the per-field migration PRs had exercised in a real browser, since sandbox has no Supabase session to reach a real edit view through. Headings (`<h1>`–`<h4>`) wrapping a field were left alone — same non-conformant content model technically, but the HTML parser doesn't auto-close a heading on block content the way it does a `<p>`, so React doesn't flag it, and there's no observed breakage.

## Photo/media system

### Storage paths vs public URLs
Supabase gives back a public URL like:
`https://<project>.supabase.co/storage/v1/object/public/portfolio-media/<user-id>/portrait-xyz.webp`

Database operations (`removeProjectPhoto`, `saveMediaPosition`, `reorderProjectPhotos`) filter by **raw storage path** (`<user-id>/portrait-xyz.webp`), not the full URL.

Always use `storagePathFromPublicUrl(url)` from `app/lib/media-path.ts` to recover the path:
```ts
export function storagePathFromPublicUrl(url: string): string | null {
  const marker = `/object/public/portfolio-media/`
  const idx = url.indexOf(marker)
  if (idx === -1) return null
  return decodeURIComponent(url.slice(idx + marker.length))
}
```

### Upload naming
Use `uniqueUploadName()` from `app/lib/image-upload.ts` → `${Date.now()}-${Math.random().toString(36).slice(2,8)}`. Prevents collisions if the user uploads the same filename twice.

### Compression (`app/lib/image-upload.ts`)
Canvas → WebP. Max edge 1920px. Target ≤ 3MB. Quality steps: `[0.95, 0.9, 0.85]` (raised from `[0.92, 0.85, 0.78]`/1.5MB after a report that project preview photos still looked a bit soft — the old 1.5MB target rarely left room for the higher-quality steps to actually get picked). Verified with a synthetic worst-case (random-noise, near-incompressible) 1600×1600 image: still lands under the new 3MB ceiling.

### Focal point / crop position
Stored as `"62% 35%"` string in `portfolio_media.position` column. Applied as CSS `objectPosition`. Edited via `PositionPicker` → `PhotoCropModal` (draggable crop frame over the full photo).

Frame math in `PhotoCropModal.tsx`:
- Frame size = percentage of photo (only the axis with slack shrinks to fit the target aspect ratio)
- `left = ((100 - frameW) * x) / 100` — maps directly to what CSS `object-position` does
- Uses `setPointerCapture` for smooth drag across browser boundaries
- Rendered via `createPortal(..., document.body)` to escape CSS `transform` containing-block traps

Rotation (optional `storagePath`/`onRotated` props on `PhotoCropModal`, threaded through `PositionPicker`): `rotateImage()` in `image-upload.ts` fetches the current photo, redraws it onto a canvas rotated 90°/180°/270° (swapping width/height for 90°/270°), and re-encodes to WebP. The caller's `onRotated(newStoragePath, newPublicUrl)` uploads-and-persists the replacement (`savePortrait`/`saveChapterPhoto` for portrait/chapter — they already delete-old-then-insert-new; `replaceProjectPhoto` for gallery photos, which updates the row in place to preserve `sort_order`). The crop position resets to center since the old frame no longer matches the rotated dimensions.

### A second, independent focal point for a photo that's a different shape on mobile than on desktop
One CSS `object-position` can't be right for two differently-shaped boxes — this became a real problem once the hero portrait went square below `md` but stayed a tall rectangle from `md` up (see the mobile-portrait CSS-conventions entries below): whatever position looked right cropped into the desktop rectangle was rarely also right cropped into the mobile square. Reported live, after the square-mobile-portrait change had already shipped: "Como hacemos para poder seleccionar una parte cuadrada de la foto asi queda centrada en el portfolio?" Asked before building (per this session's own "ask when genuinely ambiguous" convention) whether to add a second, separately-editable square frame for mobile, or go further and make the crop frame's *size* itself adjustable (real zoom, not just repositioning) — chose the former: a second focal point, not a zoom/crop-rect overhaul, since `object-position` alone already covers "which part of the cover-scaled photo shows," and this app has no per-photo scale/zoom concept anywhere else to extend.

- **`portfolio_media.position_mobile`** (migration 0016) — a second, optional `text` column alongside `position` (0004), same `"62% 35%"` format. Null falls back to the desktop `position` at render time, not to dead-center — a photo whose owner has only ever set the one (desktop) focal point should keep cropping sensibly on mobile rather than resetting.
- **`MediaImage.positionMobile`** (`portfolio.ts`) already existed as a type field and was already read by `EditableChapterPhoto.tsx`'s rendering — but nothing populated it from real data (only the hardcoded `defaultPortfolio` seed set it) and nothing let an owner set it, so it silently did nothing for a real user. `portfolio-db.ts`'s `buildMedia` now maps `row.position_mobile` into every media row generically (portrait, chapter, project photo alike), so that fallback finally reflects real data — though **only the portrait's editing UI is wired up in this pass** (see below); chapter/project photos still have no way for an owner to set their own `positionMobile`, same as before.
- **`PhotoCropModal.tsx`** — providing `mobileAspect`/`mobilePosition`/`onChangeMobile` (all three, or none) adds a `Desktop`/`Mobile` tab switcher above the existing single frame. Each tab keeps the frame math (`frameW`/`frameH`/drag) working against that tab's own `aspect`/`position`/`onChange`, so dragging one frame never touches the other's stored value — verified directly (drag the mobile-square frame, switch to the Desktop tab, confirm its frame is exactly where it was). Every other caller (chapter/project photos) passes none of the three and gets the original single-frame behavior unchanged.
- **`PositionPicker.tsx`** — same three optional props, passed straight through to the modal; its `done()` only sends `positionMobile` to `saveMediaPosition` when a mobile frame was actually provided, so a caller with no mobile frame never writes to that column at all.
- **`saveMediaPosition(storagePath, position, positionMobile?)`** — `positionMobile` is optional and omitted from the update payload entirely (not written as `null`) when not passed, so a caller without a mobile crop step (chapter/project photos, for now) can never accidentally clear another caller's mobile value for the same row. Now wrapped in its own top-level `try/catch` per this file's autosave-action convention (see "Common pitfalls" — it wasn't before this pass).
- **`EditablePortrait.tsx`** — split into two absolutely-positioned `<Image>` layers (`md:hidden` / `hidden md:block`), each with its own `objectPosition`, the same pattern `EditableChapterPhoto.tsx` already used for its own (never-wired-up) `positionMobile` fallback. `PositionPicker` gets `mobileAspect={1}` (the mobile box is a fixed square — see "Full-width (`w-full`) then turned out to be too big" below) alongside the existing `aspect={0.62}` for desktop. A new upload or a rotation resets *both* `position` and `positionMobile` to undefined — a rotated photo's old frame(s) describe dimensions that no longer exist for either shape.
- Verified in the sandbox (no live Supabase needed — pure client-side crop-tool mechanics) with a debug harness whose portrait `src` was rewritten to a path containing the `storagePathFromPublicUrl()` marker (a bare local `/public` asset otherwise resolves to a null `storagePath`, which is exactly what hides `PositionPicker` for every other local/demo image in this app): the Desktop tab shows the tall rectangular frame, the Mobile tab shows a square frame, dragging one and switching tabs leaves the other's frame exactly where it was, and clicking Done closes the modal without a thrown error (the actual save naturally fails with "You are not signed in." here, same as any other action in this session's sandbox — not something this feature could newly break).

**The two-frame tab switcher above was easy to miss entirely** — nothing about the crop tool's default state (opens on the Desktop tab, silence about there being a second one) told an owner the mobile crop existed, let alone needed setting. Reported live right after the feature shipped: "cuando seleccionas el recorte, al ser diferentes, deberia subirse la foto y decirte que selecciones las dos formas." Two additions, both in the already-existing dual-frame path (single-frame callers are untouched):
- **`PhotoCropModal.tsx`** now shows a line above the tab switcher whenever `hasMobileFrame` — "This photo shows differently on mobile and desktop — set the crop for both" — and each tab label gets a `✓` once the owner has actually opened it (`visited`, a `Set<'desktop'|'mobile'>` seeded with `'desktop'` since that tab starts active, added to via a `selectMode` wrapper around `setMode`). This is "looked at," not "confirmed a deliberate crop" — a tab's *default* position (inherited from the other shape, or dead-center) is otherwise visually indistinguishable from one the owner actually dragged, which is exactly what let this go unnoticed the first time. Resets automatically on remount (i.e. every time the modal reopens), since `visited` is local state on a component that only exists while `open`.
- **`PositionPicker.tsx`** gained an optional controlled `open`/`onOpenChange` pair (falls back to its own internal `useState` when omitted, so every caller but the one below is unaffected) — `EditablePortrait.tsx` uses it to call `setCropOpen(true)` right after a fresh upload finishes, so the crop tool now opens on its own with the "set both" hint immediately visible, rather than waiting for the owner to notice the (opacity-0-until-hover) "Adjust position" button on their own. Rotation doesn't need this — it already happens from inside an already-open modal.
- Verified live (Playwright, same debug-harness approach as above): opening via the trigger shows the hint text and "Desktop ✓ / Mobile" (only the already-active tab checked); clicking "Mobile" flips to "Desktop ✓ / Mobile ✓"; clicking back to "Desktop" keeps both checks. The auto-open-after-upload path itself needs a real Supabase session to exercise (the upload flow throws "Your session expired" before reaching the `setCropOpen(true)` call in this sandbox) — the controlled-open wiring and the hint/checkmark UI it reveals are what's covered directly.

## Onboarding: the multi-step tour

Started as a single callout pointing at the language toggle; grew into a proper multi-step tour where each step can point at a *different* element anywhere on the page (today: the language toggle, then the hero name field, then a Story chapter's drag handle, then the "+ Add project" button — more get added by appending to two parallel arrays, see below). Shown only to the owner. Explicit design, worked out over several rounds:

- **Back/Next** navigate; Back hidden on the first step; the primary button reads "Next" until the last step, where it becomes "Entendido"/"Got it".
- **A small "×" in the corner ("Salir")** closes for now without dismissing anything — it remembers which step the owner was on, so the tour resumes there next time rather than restarting at step 0.
- **"Saltear tour"**, a subtle text link, ends the tour for good from any step — a one-click "I don't want this," no checkbox needed.
- **"No volver a mostrar esto"**, a checkbox always visible, changes what "×" does: unticked, "×" just pauses (see above); ticked, "×" also ends the tour for good. It has no effect on "Saltear" or on finishing normally — both of those already mean "done," independent of the checkbox.
- Reaching the end and clicking "Entendido" always ends the tour for good, same as "Saltear" — completing it is its own reason to never show it again.

### Data model
- **`portfolios.onboarding_tour_step`** (added in migration 0014 as just a pause/resume position; migration 0015 folded a separate `onboarding_tour_seen` boolean into it and dropped that column) is the *only* piece of tour state in the database — one integer meaning "how many steps this owner has gotten through." Needs both migrations run by hand in the Supabase SQL editor, same as always.
- **Why the boolean got dropped**: it started as `language_hint_seen` (0013) — "permanently dismissed," full stop. That broke the moment the tour grew a 3rd step: an owner who had already finished the 2-step version had `seen = true` forever, so the new step never showed — reported live ("yo había hecho todo el tutorial, y ahora que agregamos pasos no me aparecieron"). A boolean has no way to say "finished everything that existed *at the time*" versus "finished, full stop" — those need to mean different things once the tour can keep growing. The single counter fixes this structurally: **`loadPortfolio`** returns `tourStep: number`, and `app/[username]/page.tsx` computes `showTour = isOwner && !previewing && portfolio.tourStep < TOUR_STEPS.length` — compared against the *current* step count every single load, not a stored flag. Appending a 4th, 5th, ... step to `TOUR_STEPS` automatically resurfaces the tour for anyone who'd finished a shorter version, landing them directly on the first step they haven't seen rather than restarting from step 0. Confirmed live: a simulated owner at progress `2` (where the tour used to end) sees the tour reopen directly on the new 3rd step, spotlight already on the right target, "Back" present, primary button already reading "Entendido" — not the first step's "Siguiente".
- **`finishOnboardingTour()`** sets `onboarding_tour_step = TOUR_STEPS.length` (read directly from `onboarding-tour.ts`, a plain shared module safe to import from a server action) — called by both "Saltear" and finishing normally (same server effect, different UI trigger). **`pauseOnboardingTour(step)`** sets it to the exact step the owner paused on — called only by "×," and only when the checkbox isn't ticked. Neither calls `revalidatePath`: the card has already closed client-side by the time either resolves, and nothing else on the page depends on the new value being reflected immediately.
- **0015's backfill is a one-time, hand-derived value (`2`), not a general formula** — read the migration's own comment before reusing this pattern elsewhere. At the moment it was written, every account that had ever finished the tour did so under the 2-step version (language toggle + name field), so `where onboarding_tour_seen = true` unconditionally becomes `onboarding_tour_step = 2` regardless of whatever stale pause-position might already be sitting in that column (finishing always supersedes an earlier pause). A future step added the same way needs no such backfill — the comparison being against `TOUR_STEPS.length` live, rather than a stored count, is exactly what makes every *subsequent* addition free.
- **Confirmed on the very next step added** (`add-project`, the "+ Add project" button in Projects, appended after the story-reorder step, no migration involved): a simulated owner with `tourStep = 3` (having finished the 3-step tour) reopens the tour directly on this 4th step — spotlight on the right target, "Back" present, primary button already "Got it" — exactly what 0015's design predicted, with zero extra backend work.

### Where the state lives, and why it moved
All of it — current step, this-session-closed, the checkbox — lives in **`LanguageContext`'s `tour`**, not in a component. It used to live in `Navbar`'s own local state, back when every step pointed at something inside `Navbar`; once a step could point at *anything on the page* (the hero name field lives in a completely different component), the state had to move somewhere both could reach, and `LanguageContext` is already the app's one shared client store. `tour.active` folds together every reason the tour might not be showing (not the owner's real editor view, already dismissed, the entrance delay hasn't elapsed, closed earlier this session) into one flag, so `OnboardingTour.tsx` only has one thing to check.

- The 2-second entrance delay (`tourReady`, a `setTimeout` inside a plain `useEffect`) lives here too, unchanged in behavior from the single-hint version — the owner's actual page content still renders immediately regardless; only the tour's first appearance is held back.

### `app/lib/onboarding-tour.ts` — the structural half
Two parallel, index-aligned arrays, deliberately kept in two different files: **`TOUR_STEPS`** here (`{id, target}` — a CSS selector matched against a `data-tour-target` attribute) is language-independent, so it lives next to the targeting logic; the actual copy (`{title, body}` per step) lives in **`translations.ts`'s `tour.steps`**, since that file is specifically the bilingual-interface-copy one. `TOUR_STEPS[i]` and `translations.<lang>.tour.steps[i]` must be added together by hand — nothing enforces the pairing at the type level.

Adding a step anywhere on the page costs exactly: one `data-tour-target="..."` attribute on the element it should point at (no import, no registration — the component that owns that element doesn't need to know the tour exists at all), one entry in `TOUR_STEPS`, and one `{title, body}` in each language's `tour.steps`.

- **`findVisibleTarget(selector)`** resolves a step's selector to the one element actually rendered right now, rather than always the first DOM match — `Navbar` renders the language toggle *twice* (desktop cluster, mobile cluster, switched by CSS media query, both always mounted), so `document.querySelectorAll` finds both and this picks whichever has a non-null `offsetParent` (a standard, cheap "this and every ancestor actually renders" check). Returns `null` if the target doesn't exist at all — a future step could point at something the owner hasn't created yet (no chapters, no projects), and the tour should skip that step's spotlight rather than point at nothing or throw.

### `app/components/OnboardingTour.tsx` — the rendering engine
One instance, rendered once from `PortfolioShell` (a sibling of `Navbar`/`main`/`Footer`/`EditBar`, not nested inside any of them — it has to be able to reach a target anywhere in that tree). Replaced the old hand-anchored version, which only worked because every step lived inside `Navbar`.

- **Positioned with `@floating-ui/react`** (`useFloating` + `offset`/`flip`/`shift`/`autoUpdate`), the same library and config shape `FloatingToolbar.tsx` already uses, `refs.setReference(target)` pointed at the real DOM node rather than a virtual reference. This is what actually fixed the single-hint version's `left-0`-vs-`right-0` overflow bug for good, rather than just patching that one case: `shift({padding: 12})` pulls the card back on-screen automatically regardless of where its target sits in the viewport, so a step pointing at anything, anywhere, stays on-screen without hand-picking an anchor side per target. Confirmed on a real 390px screenshot for both steps.
- **The current target gets scrolled into view** (`target.scrollIntoView({behavior:'smooth', block:'center'})`) when the step changes — necessary now that a step can point at something off-screen (the hero name field, on a short viewport), which was never possible when every step was pinned to the sticky navbar.
- **The spotlight ring is a CSS class (`.tour-spotlight`, in `globals.css`) applied and removed imperatively** (`target.classList.add/remove`) inside a `useEffect`, rather than each targetable component reading tour state from context and conditionally applying its own class. Adding a target costs one attribute precisely because of this — no component anywhere needs to import `useLang` or know the tour exists just to be pointed at.
- **`target` (the resolved DOM node) is computed fresh every render, not synced into `useState` by an effect.** An effect whose only job is calling `setState` — `if (!target) setTargetMissing(true)` — is exactly what `react-hooks/set-state-in-effect` flags (the same rule `Hero.tsx` and the `mounted` flag below already have to work around). `document.querySelector` is a read, not a mutation, so doing it during render is fine; it only ever runs once `mounted` is true (see below), i.e. never during SSR or the hydration-matching first client render, so the full DOM — including a target added by some *other* component elsewhere on the page — is always already committed by the time it runs. The effect that's left only does the *other* kind of `useEffect` work (mutating the DOM/floating-ui from React state), which the rule has no objection to.
- **`.tour-spotlight` needs its own `z-index` (45) and `position: relative`** — unlike the old single-target version, where the spotlighted button always happened to sit inside `Navbar`'s own `z-50` stacking context for free, a target here can be anywhere, including inside an element (like Hero's `<section>`) that establishes no stacking context of its own. Giving the target itself `position: relative; z-index: 45` directly (rather than relying on some ancestor) is what makes it pop above the dim overlay's `z-40` correctly in the general case, wherever it lives; the card floats at `z-46`, just above that.
- **`.tour-spotlight` also brightens any nested drag handle / remove button to the lime accent, `!important`.** Reported live on the story-reorder step: the drag handle and × read as "lost"/unusable even though drag-to-reorder and remove both keep working underneath, confirmed directly (a chapter really does move, really does delete) — the z-index fix above already keeps the target undimmed by the overlay, but `EditControls.tsx`'s `DragHandle`/`RemoveButton` default to a muted `text-dark-500` regardless, which is the right look everywhere else and the wrong one for a control the tour is actively pointing at and explaining. Matched generically by `[aria-label='Reorder']`/`[aria-label^='Remove']` under `.tour-spotlight`, not by which step this is, so any future step landing on some other reorder/remove control (projects, tags, contact items, ...) gets the same brightening for free — same zero-registration extensibility as the rest of the tour. `!important` is required, not stylistic: Tailwind's `text-dark-500`/`hover:text-*` utilities live in the later `utilities` layer, which beats a plain rule in this earlier `components` layer regardless of selector specificity — the same layer-order gotcha `section-padding`'s override deals with elsewhere (see Journey.tsx's own comment). Verified live: both controls render `rgb(216, 255, 62)` while spotlighted, every other chapter's controls stay at the normal muted gray, and a real drag/drop still reorders correctly with the rule in place.
- **The `mounted` flag is `useSyncExternalStore`, not `useEffect(() => setMounted(true), [])`**, for the same reason as the single-hint version this replaced: `tour.active` can be `true` on the very first (server) render since it derives from a server-computed prop, and `document.body` doesn't exist there — confirmed by `npm run build` failing to prerender a debug harness route with `ReferenceError: document is not defined` before this fix existed. `getServerSnapshot` (`() => false`) covers SSR and the hydration-matching first client render; only the real `getSnapshot` (`() => true`) takes over after that, so the portal only ever runs in a render that's guaranteed to have `document`.
- **The dim overlay and the card both fade in over 1s together** (`framer-motion`, `initial={{opacity:0}} animate={{opacity:1}} transition={{duration:1}}`, no `AnimatePresence` — only an entrance was asked for, and closing by any of the tour's own actions is a plain instant unmount). Verified against the browser's own Web Animations API (`element.getAnimations()[0].effect.getComputedTiming().duration`), not by polling computed opacity over Playwright's IPC — that has enough round-trip latency to make a component's actual start time unreliable to infer from the outside. Confirmed exactly 1000ms.
- **The overlay is `pointer-events-none`.** It's a visual cue, not a click-trap — the rest of the page stays fully interactive while the tour is up, and the card only ever closes via its own controls (×, Saltear, or reaching the end), matching the literal ask: no click-outside-to-dismiss was requested, so none was added.

## Common pitfalls
- **Always use `storagePathFromPublicUrl()`** before passing a media src to any DB action that filters by `storage_path`.
- **`NEXT_PUBLIC_*` vars** are baked at build time — never use them for secrets.
- **Supabase unreachable from sandbox** — test migrations by reading the SQL file, never by running `supabase db push` or similar.
- **Empty `contentEditable`** — add `editable-field` class + `data-placeholder` or the field collapses to zero size and becomes unclickable.
- **`dirty` guard** — EditBar registers `beforeunload` when dirty; always call `markSaved()` after a successful save.
- **A save-path sanitizer's `list(...).filter(...)` can silently delete a work-in-progress entry** — `portfolio-actions.ts`'s `contact.socials` sanitizer used to `.filter((s) => s.label && s.url)` (both required), so filling in just the label and saving before getting to the URL deleted the whole entry on the very next save, with no error — reported as "I add a label but can't edit it" (it wasn't uneditable; it kept vanishing). An **AND** filter across a multi-field item's fields almost always wants to be an **OR** (drop only a *fully* empty entry) unless there's a real reason a lone field is meaningless on its own. Compounding this one: `url()`'s `new URL(raw)` rejects a bare domain typed without a scheme (the natural way to type one, e.g. `linkedin.com/in/you`) — silently sanitized to `''`, which then tripped the AND filter too. Fixed by normalizing a schemeless value to `https://<value>` first (mirroring `LinkPopover.tsx`'s own link normalizer) *and* switching to OR. `Contact.tsx`/`Footer.tsx`'s public-read rendering both need `social.url ? <a href={social.url}>... : <span>...` guards to match — an `<a href="">` for a label-only entry silently links to the current page instead of doing nothing.
- **Every autosave-path server action (`block-actions.ts`'s `upsertBlock`, every function in `block-list-actions.ts`, `portfolio-actions.ts`'s `savePortfolio`) is wrapped in its own top-level `try/catch`, returning `{ok:false, error}` on an unexpected throw rather than ever letting the call reject.** Added after "Saving se queda trabado, no cambia nunca" (reported live, after the try/catch in `useBlockPersistence.save()` — see EditBar's section — was already in place): that fix stopped the *global* saving indicator from getting stuck, but the actual save call was still capable of rejecting for reasons with no error text at all, which is what a thrown-not-returned failure looks like from the caller's side — `useBlockPersistence`'s own catch only knows a request failed, not why, so it shows a generic "Could not save this field." fallback. Catching inside the action itself is what surfaces the *real* message (whatever the thrown error's `.message` is) instead of that generic text, which is what makes the next occurrence diagnosable from a screenshot alone. Every one of these actions already returns `{ok:false, error}` on an *expected* failure (no user, no portfolio row, a Postgres error) — this only covers the unexpected kind, e.g. a Supabase client call throwing outright rather than resolving with an `error` field.
